# 投稿画像のバックエンドサムネイル

`thumbnail.backend` で公開GET APIを設定します。

```json
"backend": {
    "use": true,
    "url": "https://armd-01.sakura.ne.jp/community-mapmaker-backend/api/thumbnail.php?app=jusoartfes2026"
}
```

バックエンドの画像項目は `image` 型である必要があります。フロントのフォームでは対応する項目を従来どおり `image_url` として指定します。APIには投稿の `id` と画像項目名 `field` を渡し、ブラウザから認証情報や任意URLのPOSTは送りません。

対象は、地図の写真アイコン、下部の画像一覧、投稿詳細内の縮小画像です。APIが返す長辺400px以内の画像を使用します。同じ画像はページ内で共有し、APIへのリクエストを直列化してサーバーの同時生成制限を避けます。一時的な503は最大2回再試行し、429や設定不整合の422では一定時間APIリクエストを控えます。取得失敗時は元画像で表示します。

拡大ビューアでは `data-original-src` の元URLを使います。Wikimedia Commonsは `src_org` を優先します。投稿の保存データ、原寸の画像ビューア、額縁内の画像、資料画像の表示先URLは書き換えません。

`./yodokabe/...` などの相対パス、`File:...`、投稿に紐づかないOSM画像はこのAPIへ送りません。Commonsは従来の縮小画像取得を利用します。相対パスの画像は元ファイルを表示します。

設定がない場合、または `use: false` の場合は従来動作です。

確認: `node tests/backend-thumbnails.cjs`。APIとの実接続には対象Projectの画像項目の型が正しく設定されている必要があります。

実接続確認（2026年11月9日）: `WP/2205` の `picture_url1` は元画像678,802バイト（1477×1108）から、サムネイル35,766バイト（400×300、WebP）となり、約94.7%削減。ブラウザで地図・一覧・詳細の縮小表示に同じ生成画像を共有し、拡大ビューアが元画像URLを開くことを確認しました。

同日、バックエンド修正後に日本語ファイル名の `WP/1506` / `picture_url1` もHTTP 200を確認。元画像386,114バイト（2048×2560）から、サムネイル14,748バイト（320×400、WebP）となり、約96.2%削減しました。
